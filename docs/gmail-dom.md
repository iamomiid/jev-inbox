# Gmail DOM

The content script reads the message list out of Gmail's rendered markup. It reorders Gmail's own rows on screen and writes chips into them, but only in the list views the popup enables. It never moves a row in the DOM: Gmail maps a row to its thread by the row's position in the list, so a moved row would open, select, or act on the wrong mail. Everything below is brittle by nature: Gmail ships obfuscated class names and changes them without notice.

## Views

`currentView()` classifies `location.hash` once a visible `div[role=main]` with a `tr.zA` row exists. Without one, the view is null and nothing is injected.

- inbox: empty hash, `#inbox`, `#inbox?...`, including `#inbox?compose=...`.
- tabs: `#category/<name>`, so promotions, social, updates, forums.
- search: `#search/<query>`, `#advanced-search/...`.
- other: every other hash that lists mail: `#label/<name>`, `#starred`, `#imp`, `#all`, `#sent`, `#drafts`, and the rest.
- null: a hash whose thread id segment is a list segment plus a thread id. A thread id is the last segment when it is 16 or more `[A-Za-z0-9]` characters and it sits after the list part: one list segment for `inbox`, `starred`, `all`, `sent`, `drafts` and the rest, so `#inbox/FMfcg...` and `#starred/FMfcg...`; two list segments for `search`, `advanced-search`, `label`, `category`, so `#search/is%3Aunread/FMfcg...`, `#label/Work/FMfcg...`, `#category/social/FMfcg...`. A search or label query in list position that happens to be 16 or more alphanumerics, such as `#search/abcdefghijklmno123`, stays a list view.

`?` and everything after it is stripped before the hash is split on `/`, and each segment is decoded with `decodeURIComponent`.

Each view has a setting, in the popup under "Show on": `viewInbox` (on), `viewTabs` (on), `viewSearch` (on), `viewOther` (off). Settings live in `chrome.storage.local` and changes arrive on `chrome.storage.onChanged`. A view that is off sends no classify requests and gets its rows, chips, and bar restored and removed.

The provider is a setting too: `provider` is `gateway` or `typesafe` (default `gateway`), with one key per provider, `apiKey` for Vercel AI Gateway and `typesafeApiKey` for TypeSafe. The popup shows only the chosen provider's key field, and it never reads a stored key back: `apiKeyHint` and `typesafeApiKeyHint` hold the last four characters of each key, the popup shows "Key saved, ends in ..." from them, and Replace writes a new key and hint while Remove deletes both. The content script reads the settings by name and never the two keys: it names `provider`, `enabled`, `threshold`, `labels`, `privacyAck`, and the four view keys in its `chrome.storage.local.get` call, and reaches the cache through `getKeys()` filtered to the `crit:` prefix. A browser without `getKeys` (before Chrome 130) warms no cache and reclassifies everything through the worker.

## Selectors

- Visible main: `div[role=main]` with a computed display other than `none`, a set `offsetParent`, and a `tr.zA` row inside. The first match wins.
- Visible list: the first `.Cp` in main that holds a `tr.zA` and has a set `offsetParent` or a non-empty `getClientRects()`. Gmail keeps several `.Cp` elements in the page (hidden tabs, previous views), so the first `.Cp` is usually not the live one. Only rows inside this list are ordered, chipped, or classified.
- Bar placement: the bar `div#gc-unread` is inserted as a child of the visible list's parent, immediately before the visible list. Switching views moves that same node, so only one bar ever exists.
- Rows: `tr.zA.zE` is an unread row, where `zA` is the row class and `zE` marks unread. Read rows are `tr.zA` without `zE` (seen as `zA yO`): they are never classified or chipped, but they take part in the order.
- Row thread id: the first `[data-thread-id]` inside the row, in practice on `span.bqe`. It identifies the row when the list's original order is recorded. A row without one takes no part in the order and drifts below the ordered rows.
- Sender: `span.zF[email][name]`. `name` is the display name, `email` the address.
- Subject and ids: `span.bqe[data-thread-id]`. Text content is the subject. Attributes used:
  - `data-thread-id`: with the last message id and the labels hash, forms the classification cache key.
  - `data-legacy-thread-id`: Gmail's own open-thread target.
  - `data-legacy-last-message-id`: the rest of the cache key.
- Subject cell: `div.y6` holds the subject, `span.bog` wraps it, and `span.bqe` is the subject element on unread rows. The chips span is inserted inside `div.y6`, immediately before the subject, falling back to immediately before `span.bog` or `span.bqe`.
- Snippet: `span.y2`, with nested `span.Zt` removed before reading text. `Zt` holds Gmail's leading separator.
- Date: the `title` of `td.xW span[title]`, falling back to the text of `td.xW`.
- A row missing the sender, the subject element, or any of the three ids is skipped.
- The script never touches row clicks or `location.hash`, and never moves a row in the DOM: Gmail's own row actions, selection, and navigation keep working, because every row stays at the position Gmail gave it.

## Unread bar and row order

- The bar shows `M unread` for the classifiable unread rows of the visible list. While a dispatch is in flight and some of those rows carry no classification, it adds an indeterminate progress line, a `span.gc-progress` animated from `currentColor`, and `Classifying N of M unread`, where N is the unclassified count and M the total. One error line appears when the last dispatch failed. Every write goes through `render()`, which rewrites the bar only when the count, the in-flight count, or the error text changes. Its left padding is measured once per placement from the first row's content, so the text lines up with the rows instead of the list edge.
- Order: the order is visual only. Every row keeps its place in the `tbody` and carries an inline `translateY` that takes it from its own slot to its target slot, so the list keeps its height and does not reflow. Slots are the rows' own layout positions, measured as each row's bounding rect top minus the translate currently on it, so neither Gmail's inline transforms nor the script's own enter the measurement; the k-th row in target order takes the k-th slot, slots read in DOM order, so anything Gmail puts between two rows stays where it is and rows flow around it. A row taller than its slot is pushed below the previous row, and a row that would reach into a gap that holds something else, a separator or a sponsored row, is pushed below that gap, so rows overlap neither each other nor that content. A write composes with Gmail's own inline `transform`: the value written is Gmail's current value plus the `translateY`, or Gmail's value alone when the offset is 0, and Gmail's value becomes the new baseline whenever it differs from the one last written. Unread rows (`tr.zA.zE`) go first: critical rows first, where critical means `criticalProbability` at or above the threshold setting, sorted by urgency score descending then critical probability descending, then every other unread row, unclassified and failed rows included; then every read row. Inside the two non-critical groups rows keep Gmail's own relative order. Rows with no thread id take no part in the ranking and sit last. A row whose target slot is the slot it already has gets its original inline `transform` back, and a transform is written only when the value changes.
- Timing: the MutationObserver callback runs the whole order pass itself, synchronously, so the transforms land in a microtask before the next paint and Gmail's default order is never painted after a re-render. The pass is coalesced: it runs once per task, with a flag cleared in a microtask, and it only runs when a foreign record touches the visible list or an added or removed node contains a `tr.zA`; a foreign record that touches neither is ignored, so unrelated page churn never defers classification. A second observer watches `class` on the rows of the visible list, so a row that gains or loses `zE` without a re-render gets its chips, the unread block, and the count updated in the same way. The debounced `sync()` (800 ms) only discovers rows that need classification and dispatches them; ordering never waits on it. A `ResizeObserver` on the visible list and its rows runs the same pass when a box changes size, so a density switch, a window resize, or a late font load re-measures the offsets; a transform never changes a row's box, so that observer cannot retrigger itself.
- Classifications: a content-script map keyed by the cache key holds every classification the tab has seen. Bootstrap fills it from the `crit:` entries the current cache version matches, read through `getKeys()`. Dispatch responses and `chrome.storage.onChanged` for `crit:` entries written by other tabs keep it current. The map survives list re-renders, scrolling, and navigation, and is cleared when the labels or the provider change or the cache is cleared, which sends those rows back through classification.
- Chips: a `span.gc-chips` inside each classifiable unread row holds a `Critical` badge on critical rows, one chip per label whose probability is at or above the threshold, a pulsing `span.gc-dot` while the row has no result, and a muted `retrying` while the row backs off after a failure. A row that becomes read loses its chips, and a classified row with no badge and no chip above the threshold carries no slot at all, so nothing indents its subject. A row is rewritten only when its badge, chips, or marker change.
- Animation: when a classification arrives and rows change their offset, each row that moves gets `transition: transform 180ms` and its new `translateY`, so it slides from its old slot to its new one, and its own inline `transition` goes back 250 ms later, unless Gmail wrote a newer one meanwhile. Moves from a Gmail re-render, a class change, a resize, or any other pass are instant, and `prefers-reduced-motion: reduce` turns the animation off.
- Restore: on disable, a view turned off, a list change, or navigation, every row gets its own inline `transform` and `transition` back, each written only while the row still carries the value the script last applied, so a newer Gmail value survives; the chips are removed and the bar is removed. Gmail's own DOM order is the only baseline the script needs, so no order is recorded across passes. A disable or a view toggle restores in the same task as the storage change, without waiting for the debounced `sync()`.
- Keyboard: Gmail's `j`/`k` and its arrow selection walk Gmail's own DOM order, which is not the order on screen, so the selection jumps between slots as it moves down the list. That is expected and is not corrected.
- Chip hue comes from a fixed set of eight hues indexed by the label's position in the settings list. The bar, the badge, and the chips mix their hue and `currentColor`, so they read on Gmail's light, dark, and custom themes.
- The labels themselves live in `chrome.storage.local` as `labels: { id, name, description }[]`, edited in the popup, capped at 15. Changes apply live. A label with an empty name or description is not saved; the popup shows an inline message and keeps the previous set.
- `render()` writes nothing when the order already matches, the bar text is unchanged, and every row carries the chips signature for its current state. After its own writes it drops both observers' pending records with `observer.takeRecords()` and `classObserver.takeRecords()`, and the childList observer ignores records inside the bar or carrying only `gc-` elements, so a pass cannot retrigger itself. The childList observer watches `childList` only, the class observer watches `class` on the rows of the visible list only, and the `ResizeObserver` watches box sizes only, so the `transform` and `transition` writes a pass makes reach none of them.

## Classify flow

- The content script sends `{ type: 'classify', emails, labels }` to the service worker and receives `{ ok: true, results, errors }` or `{ ok: false, error }`. The worker settles the provider from the `provider` setting and its key from `apiKey` or `typesafeApiKey`, and results are keyed by thread id plus last message id plus provider plus the labels hash. Until the popup has stored `privacyAck: true` the worker answers `needs_ack`, the bar reads `Open Jev Inbox to finish setup.`, and classification halts until that setting arrives, so no row ever reaches a provider before the first-run notice is acknowledged. The worker also answers `{ type: 'test' }` with one boolean question on a fixed dummy state, which the popup's "Test connection" button uses and which sends no email data. It answers `needs_ack` for that message too until the first-run notice is accepted, and the popup keeps the button disabled until then.
- Batches of 20 rows go out one at a time, at most one dispatch in flight. Before each batch and after each response the loop checks that the extension is still enabled, the view is still on, the visible list node is unchanged, and the generation counter has not moved. The counter moves on `hashchange` and on any storage change to `enabled`, `labels`, `provider`, or a view toggle, so a result that arrives after a navigation, a disable, or a provider or label edit is dropped.
- Cache: `crit:` prefixed entries in `chrome.storage.local`, keyed by thread id, last message id, provider, and the labels hash. Editing labels changes the hash and switching the provider changes the prefix, so the visible rows reclassify; old entries stay until "Clear cache" removes them. Only the service worker writes them; the content script follows later changes. Each entry carries the `ts` of its write. Once the `crit:` entries pass 5000, the worker deletes the oldest by `ts` down to 4000 after the next dispatch that wrote an entry. A write that fails (quota or anything else) is logged and the classification still reaches the content script.
- Concurrent misses for the same cache key share one evaluate call. The worker rechecks storage before starting, reuses an in-flight promise, and drops the entry when the promise settles, so a failure is never cached.
- A failed row backs off: 60 s after the first failure, doubling per consecutive failure up to 10 min. The failure count and deadline live in a map keyed by the cache key, not on the row, so they survive navigation and Gmail replacing the rows; the map clears when a result arrives, the labels or the provider change, either key changes, or the entry leaves the cache. After each dispatch the content script arms one timer for the earliest pending retry, replaces it on the next dispatch, and clears it when the bar is removed, the extension is disabled, or the view is off. A 401 or 403 on any row stops the whole batch: no worker dequeues further emails, calls already in flight may finish, and the content script halts until either key or the provider changes. A missing key halts the same way.

## When Gmail changes

Check in this order:

1. Rows still match `tr.zA.zE`. If unread rows lose `zE` (or `zA`), they stop being classified and chipped and mix into the read rows; the class observer drops their chips as soon as Gmail rewrites the row.
2. The thread id still sits on `[data-thread-id]` inside the row, and `span.bqe` still carries all three `data-` ids. Missing ids mean the row is never ranked and stays at the bottom of the visual order.
3. `div.y6` still holds the subject and `span.bog` still wraps it. If the subject cell is rewrapped, chips stop being inserted.
4. `span.y2` is still the snippet and `span.Zt` is still the separator to strip.
5. The visible `.Cp` is still the list container, so rows are still moved visually and the bar still lands above the list. If Gmail wraps or renames it, nothing is injected on any view.
6. `div[role=main]` is still the visible list container.
7. Hash routes still look like `#inbox`, `#category/<name>`, `#search/<query>`, `#label/<name>`. A renamed route lands that view in "Labels and other folders" or switches the injection off.
